# How it works

- `src/entrypoints/gmail.content.ts` hides Gmail's DOM at document start, mounts the app in an extension iframe over the page, and hands it a `MessagePort` to the session backend. It also keeps the tab title, unread favicon and URL hash in sync.
- `src/entrypoints/gmail-main.content.ts` (main world; injected as `gmail-main-safari.js` on Safari) copies the tokens Gmail's own requests carry so the session backend can call the same endpoints.
- `safari-app/` is the Mac app's window (Swift and a small web page) and its icon (`AppIcon.icon`, an Icon Composer document; open it in Icon Composer to edit), copied into the generated Xcode project by `scripts/package-safari.sh`. Its switch opens `https://mail.google.com/mail/u/0/#better-gmail=on` (or `=off`) in the chosen browser; the content script reads that only when the page was opened from outside the browser, with no referrer (`src/shared/switch-link.ts`), then reloads the other Gmail tabs.
- `src/app/` is the UI: React 19, Base UI primitives, TanStack Query with optimistic updates and undo, Zustand for UI state. Every backend implements `src/app/data/backend.ts`.
- `src/session/`, `src/app/data/api/`, `src/app/data/demo/` are the three backends.
- On reload the inbox paints from a small cache before Gmail's session is ready: the first page of the inbox, the labels and the account, per account (keyed by the address Gmail's page names before its first sync) and per backend, in extension storage only (`src/app/data/bootCache.ts`). It shows with a refreshing bar until the backend answers, and actions taken meanwhile wait for that fresh data. Switching to classic Gmail, turning the extension off, signing out or changing the mail source clears it.
- Requests are budgeted. One sync loop (`src/app/data/sync.ts`) keeps mail live: every 20 seconds while the tab is visible it asks what changed since the last history id (Gmail's own sync delta in session mode, `history.list` with the Gmail API) and refreshes only the lists and thread on screen, the label counts and the changed threads; other cached lists are marked stale for their next visit, and the smart searches (At a glance, category tabs, Purchases) run again on new mail at most every five minutes. A hidden tab asks for nothing and catches up with one poll when you come back. Queries don't refetch on focus or reconnect, failures back off with jitter (a rate limit waits at least a minute), and identical requests in flight are shared. Idle, that's three small polls a minute; new mail adds a list page and the label counts. Low-priority searches nobody is waiting on go through `backgroundSearch()` (`src/app/data/backgroundQueue.ts`): a token bucket, idle time only, cached. In development `window.__bgRequests` counts backend calls; `tests/api/request-budget.test.ts` holds the budget.
- Other signed-in accounts (session mode): the content script lists them from Gmail's atom feed (`/mail/u/N/feed/atom`, an address and an unread count per slot, without loading Gmail); names and photos come from each account's own page once it has been opened, and from Google's signed-in account list (`accounts.google.com/ListAccounts`, the reason for that host permission) when it answers. Switching to one account loads `/mail/u/N/` in the tab, the way Gmail switches. Each account's page saves the headers its own sync calls carry (`src/session/stored.ts`, in extension storage on this device), and All inboxes and circles read every account with those from the current page (`src/app/data/accounts/merged.ts`: lists merged newest first, ids qualified as `<account key>~<id>`, user labels matched by name, writes sent to the owning account). An account not opened in this browser yet says so, with a button to open it. The demo has three fictional accounts; the Gmail API source reaches one.
- Recipient suggestions use the same engine Gmail's compose does. In session mode that's Google's People Stack autocomplete (`peoplestack-pa.clients6.google.com`, called from the Gmail page with its own sign-in, as Gmail does; `src/session/contacts.ts`); with the Gmail API it's People API `searchContacts` and `otherContacts:search` after their warmup request. Its answers are ranked together with people you've corresponded with, indexed in this browser from mail the app loads plus one look at recent Sent mail, and with your own addresses and send-as aliases (`src/app/data/contacts.ts`): Google's order, lifted for people you also mail, a match at the start of a name or address above one inside it. A request goes out only once typing pauses, answers are kept per prefix (a longer prefix is answered from a shorter one that came back complete), and when Google's endpoint fails the local suggestions carry on alone. Profile photos come from the backend's `lookupPhotos`: in session mode, first the pictures Gmail puts beside a sender in its own mail data (verified senders' logos arrive inline as `data:image/png`), then People Stack Lookup (the call Gmail makes for every sender it shows, contacts or not, 25 addresses a request, in the shape the page's own calls use once it has made one); with the Gmail API, one listing of saved and other contacts (the API can't see other people's photos). Settings > Connection > Photos lists the last 30 lookups, with addresses reduced to their domain, for pasting into a bug report. Organisations (no-reply@, news@ and the like) also get a logo from Google's favicon service, tried for the sender's own subdomain and then its registrable domain, never from the sender's own site; Gmail's own logo wins when there is one. Both are cached per account, misses for a day (`src/app/data/photos.ts`, `src/app/data/brands.ts`). A photo that won't load in the app's frame (some Chromium browsers, like Dia, don't send Google's cookies there) falls back to a copy the extension reads, then its public address, then a fresh lookup, then the initial (`src/app/ui/Avatar.tsx`).
- Schedule send is Gmail's own, so the message waits in Gmail's Scheduled folder and Google's servers send it whether or not the browser is running. No open-source project documents a sync request that schedules or cancels (gmail.js, PR #567, only spots a scheduled send in Gmail's traffic by its `^scheduled` label), so session mode does it the way InboxSDK does (`getScheduleSendButton` / `openScheduleSendMenu`): the app saves the message as a Gmail draft through the sync API, then the page hidden under the app (`src/session/gmail-page.ts`) opens that draft (`#drafts?compose=<id>`, InboxSDK's `encodeDraftUrlId`), opens the arrow next to Send, picks Schedule send (`[selector="scheduledSend"]`), then Gmail's preset when it names exactly the chosen minute or Pick date & time with Gmail's date and time fields, and presses Schedule send. When the arrow's menu doesn't open, it presses Schedule send where Gmail keeps it in the compose window, as InboxSDK does. It never presses Send. Every step has a time limit and the whole run 45 seconds; on failure it closes the dialogs and compose window it opened (Gmail saves the draft as it closes), puts the address back, and the app reopens your message with the draft it saved, naming the step Gmail stopped at. A retry for the same draft while one is still running joins it rather than scheduling twice, and if Gmail hasn't answered in 90 seconds the window comes back anyway, with the late answer reported when it arrives. The sync API re-read is the judge: the message has to come back under `^scheduled` at the chosen time, or the app says "Couldn't schedule in Gmail. Your message is saved in Drafts." and offers the draft in classic Gmail (a different time is cancelled again). Cancel send, Undo and Edit open the message from Gmail's Scheduled folder on the same page and press Gmail's Cancel send, which returns it to Drafts. Only the tab's own account has that page, so other accounts can't schedule from here; the Gmail API source can't schedule at all, and the menu says so. The demo schedules on its own side; `?schedule=off` shows the menu without scheduling.
- The installed app (`src/shared/pwa-host.ts`, started by the content script at document start). Every app API belongs to the top page on mail.google.com, not the extension frame, so the content script owns them and the frame asks for them through `src/app/lib/appHost.ts`. It gives the page a web app manifest of its own as a `data:` URL (every URL in it absolute, the icons read from the extension into `data:` URLs too) in place of any manifest Gmail's page has, colored to the app's theme and rewritten when the theme changes, with one `id` for every account so the browser sees one app. It also sets the page's `theme-color`, so the app window's title bar matches. The manifest lists shortcuts, a `mailto:` protocol handler, a GET share target and file handlers, all launching `/mail/u/N/?expressive=…` URLs; with `launch_handler: focus-existing`, a launch into an open window comes through the launch queue and is handled in place instead of reloading Gmail. A launch URL is read and taken out of the address bar before Gmail's page can act on it, and handed to the app frame once it says hello. Gmail's own `?extsrc=mailto` URL is read the same way. The browser's install offer (`beforeinstallprompt`) is kept for Settings > App; the click in the frame counts as the page's, so the page may show the browser's dialog. The icon badge is the inbox's unread count, a dot or nothing (`appBadge`). Safari gets no manifest: its web apps run no extensions, so an app installed from there would open plain Gmail.
- Design tokens come from Google's Compose Material 3 token files: `src/app/theme/tokens.css`. See [DESIGN.md](../DESIGN.md).

## Known limits

- The session backend is built from open-source reverse engineering (InboxSDK, gmail.js) and fixtures; it hasn't been exercised against every Gmail account type. If your inbox doesn't load, switch to the Gmail API in Settings > Connection and report what you saw.
- All inboxes and circles in session mode depend on sessions saved when each account's page last ran. If Google stops honoring one (a sign-out, or a session that expired), that account shows "Open it once" until its page runs again. The Gmail API source reaches one account.
- Session mode can't create, rename or delete labels or edit filters yet.
- Schedule send and Cancel send in session mode press Gmail's own buttons on the page hidden under the app (see How it works), for the tab's own account only. Most steps use hooks that don't depend on Gmail's language (the draft field, `selector="scheduledSend"`, dialog roles, the date and time fields in order, the dialog's OK button), with English names as the fallback; Cancel send is found by its English name only. Tested against a stand-in Gmail page in English and French, not yet against live Gmail in other languages. If Gmail's page doesn't respond, nothing is sent and the message stays in Drafts.
- Delete forever, Empty Trash now and Delete all spam now in session mode press Gmail's own buttons on the page hidden under the app (`src/session/gmail-page.ts`), then re-read the folder through the sync API until Gmail lists nothing there; no known sync request deletes forever. That needs Gmail in English and works for the tab's own account only; otherwise, or if Gmail's page doesn't respond, the app says so and offers classic Gmail.
- The installed app uses no service worker (an extension can't register one on mail.google.com), so it works offline only as far as the boot cache goes, and its title bar is the browser's own, tinted to the theme, rather than a window controls overlay: the app's frame can't mark parts of itself as the window's drag area. The manifest has been checked in Chromium (it parses, and the page counts as installable), not yet against live Gmail, whose content security policy could refuse a `data:` manifest.
